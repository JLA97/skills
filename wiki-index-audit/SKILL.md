# Wiki 检索与页面边界审计

目标：让问题容易找到有依据的答案，减少重复阅读，让页面围绕清楚的任务组织。字数、关键词重合和跳转次数只产生候选；不能单独证明需要合并或拆页。

审计连着检查 README 路由、`关键认知索引.md` 和专题正文。`sync-docs-index` 负责执行摘要、标题和路由同步；本 Skill 判断这些入口及页面边界是否合理。

## 1. 扫描

在 Wiki 根目录运行本 Skill 的 `scripts/audit_index.py`，将 `<skill-dir>` 替换为本次实际读取的技能目录，避免硬编码安装路径：

```bash
python3 <skill-dir>/scripts/audit_index.py --root . --format json --output /tmp/wiki-audit-scan.json
```

脚本扫描非隐藏目录内的 Markdown，输出页面摘要、章节位置与规模、README 入口、内部链接问题、原样重复段落、共用来源的卡片组和体积较大的页面。配置与旧基线存在时读取，不要求创建文件。`--mode quick/full` 仅兼容旧命令，均执行同一扫描。

脚本的 `mechanical_status` 只反映机械检查，`semantic_status` 始终为 `pending`。退出码 0 表示扫描成功；2 表示输入或解析失败。脚本不判定 Wiki 健康，也不更新基线。

## 2. 按主题复核

先浏览全部 README 路由和页面摘要/标题，补充脚本未发现的相近主题。按风险选取断路由、疑似重复、页面边界不清的候选，连着读相关导航、卡片和正文。候选为零也不能省略导航与边界复核。

| 检查 | 判断依据 | 优先动作 |
|---|---|---|
| 检索入口 | README、卡片是否指向正确页/章节；标题和摘要能否让人判断何时阅读 | 修路由、标题、摘要或章节链接 |
| 冗余 | 多处完整维护同一判断/流程/案例，是否增加阅读成本或产生冲突 | 保留完整正文真源，其他处缩成摘要与引用；保留必要的导航重复 |
| 过度拆分 | 页面缺少独立用途，必须连续读取相邻页才能理解，或重复背景、割裂论证 | 合并或回归父页，同时保留有用入口与独立判断 |
| 过度拥挤 | 多个独立任务混在一页，标题/摘要难概括，章节入口仍难以定位 | 先改章节和导航，再评估拆页 |

拆页需回答：新页独立解决什么任务？能否独立理解并有入口？减少的无关阅读是否值得新增跳转与维护成本？合并需说明各页独有内容如何保留。共同出现的页面可能是合理分工，不能按共现直接判重复。

用具体正文段落支撑判断，必要时回查卡片来源与版本；矛盾会使行动相反时优先处理。真实查询案例有则记录原问题、实际路由和遗漏/误触发点，并解释原因；无则注明“实际查询效果未验证”，不构造固定召回测试，不要求 `retrieval-evals.json`。

## 3. 报告与确认后修复

报告只保留两张表：

1. **实际复核范围**：主题、已读文件/章节、检查结果、尚未核验范围。区分全库机械扫描、导航浏览与正文复核，不能用部分阅读宣称全库健康。
2. **最小变更集**：优先级、当前障碍及位置/证据、建议修改、预期改善、需保留内容。阈值候选经复核合理时说明保留原因，不算内容缺陷。

P0：关键来源缺失/否定判断；P1：同场景会采取相反行动或关键检索路径失效；P2：冗余、边界或定位障碍；P3：措辞与导航优化。先做路由、标题、引用等小改动，再考虑合并拆页。无问题也给出已检查范围与限制。

默认只报告，临时输出放 `/tmp`，用户要求保留时再存仓库。仅在用户确认具体变更集后修改 Wiki：先修正文，再同步卡片与 README，保留独有判断和证据；复跑扫描并重读受影响主题。有真实原问题时重走其检索路径，无案例则只报告结构复验。基线仅是规模参考，不可用刷新基线表示语义问题已解决。

月度或大规模新增/重构后运行；Automation 同样停在报告阶段。
