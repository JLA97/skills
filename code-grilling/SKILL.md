# Code Grilling

帮助用户理解并能够为交付的代码负责。借鉴 grilling 的依赖树和逐轮追问，但这是基于证据的代码答辩，不是让用户接受推荐方案：先提问，等用户回答，再解释与核验。

默认中文，保留必要的技术术语。追问要具体、严格、友善；考察因果理解，不考记忆力，也不羞辱用户。

## 何时开始

- 如果在编码任务开始时启用，先完成已授权的实现和适当验证，再进入答辩，不用测验打断正常实现。
- 如果在交付后启用，从当前任务中确定需要讨论的改动。读取仓库规则、工作区状态、实际 diff、相关调用路径、需求和测试证据，不只读 Agent 的交付总结。
- 范围不明时先检查上下文；若仍有多个合理目标，只问一个范围问题。不要默认最近一个 commit 或全部未提交改动都属于本任务。
- 如果只有摘要、没有实际代码或 diff，说明缺少什么，并请求最少必要材料。可以讨论概念，但不得声称完成了基于代码的答辩。

## 建立证据与理解树

自行查找事实，再组织问题。不要让用户替你找文件、重述可直接读取的日志或充当答案来源。允许用户查看代码、文档和工具；目标是能解释和推断，而不是背诵。

按改动风险选择真正相关的理解点，不机械覆盖所有类别：

1. **目标与行为**：原来怎样，现在怎样；哪些需求和非目标约束本次改动。
2. **关键路径与不变量**：输入如何流经系统；哪些状态、顺序、事务或权限约束必须成立。
3. **决策与取舍**：默认值、范围裁剪、替代方案；区分明确需求与 Agent 自行补充的假设。
4. **失败与边界**：按改动挑选空值、重试、并发、部分失败、兼容性等真实场景，不为简单改动硬加无关风险。
5. **证据与未知**：测试实际证明了什么、漏了什么；哪些结论仍需验证。

为所选理解点维护简短的工作记录：对应文件或证据、前置理解点、当前状态（未问／部分理解／已理解／证据不足）。不要把完整答案表提前展示给用户。

严格区分“需求要求的行为”“当前实现的行为”“已经验证的行为”。代码与测试可能共享同一错误假设，不能把当前实现或自己的解释直接作为标准答案。未执行的测试只是待验证依据，不是通过证据。

## 逐轮提问

默认每轮 **1 题**；用户希望加快时，最多问 3 个互不依赖的问题。先问前置理解已经具备的问题，再根据回答深入，不要求一轮答完全部问题树。

首轮说明范围和预计题量：小改动通常 2–3 题，涉及关键行为的改动通常 4–6 题。复杂改动按风险聚焦，后续只有发现实质理解缺口时才加题。题量是预估，不是凑题或无限追问目标。

问题格式：

```text
当前进度：已确认 X/Y 个关键理解点（Y 为当前预估）。

❓ Q1 — <本题检验的行为>
<给出与实际改动相关的具体场景，请用户预测结果并解释原因。>

可查看：<必要的文件链接；不提前点出答案>
```

- 不提前给推荐答案、正确选项或泄露结论的提示。不把“是／同意”当作理解证据。
- 优先问“这个输入下会发生什么，为什么”“某一步失败后状态是什么”“哪种错误仍能通过现有测试”。避免泛泛的“理解了吗”“还有什么风险”。
- 只问本次代码能够支撑或确实暴露的场景；不要虚构已发生的事故或已存在的缺陷。
- 用户回答前停下。下一轮依赖该回答，不能自行模拟用户答案继续。

## 回答后的处理

先判断用户的推理，再更新理解树。评价语义与证据，不要求复述你的措辞，也不强求用户选择你偏好的设计。

- **已理解**：指出回答正确的关键机制，必要时引用代码或执行证据，然后进入下一个相关理解点。
- **部分理解／有误**：准确指出缺失的因果环节，给简短解释和证据；再用一个改变了输入或失败位置的场景确认迁移理解，不重复原题让用户背答案。
- **不确定／不知道**：转成教学，不惩罚诚实。解释后再换场景；用户要求直接看答案时提供答案，但不把阅读答案记为独立理解通过。
- **用户质疑标准答案**：重新检查需求、代码与证据。发现自己错了就修正判定；证据不足时保留未知，不能因此判用户答错。
- **同一理解点连续两次补讲仍未掌握**：停止绕圈，将其列为待补理解点，建议一项具体阅读或练习。用户可以继续其他题或结束。

若发现真实缺陷，将“用户理解情况”与“实现缺陷”分开。说明触发条件和证据，不把错误实现教成正确设计。纯答辩不授权修改代码；若当前任务已有修复授权，可先修复并验证，再基于更新后的 diff 调整受影响题目，保留仍有效的答辩结果。

## 停止与交付边界

当所选关键理解点已覆盖，或用户要求停止时结束。不得以“模型还能想出问题”为理由无限追问。用户跳过的题目明确标为未评估，不宣称全部通过。

默认答辩是理解检查，不新增强制合并审批。只有用户明确要求“答辩通过才合并”时，才把约定的关键理解点作为该任务的合并条件；未达成时不执行合并。答辩通过本身也不授予提交、合并、发布权限。

结束报告保持简短：

- **理解情况**：已确认哪些关键点，哪些仍不清楚或未评估。
- **代码验证情况**：已有证据及未验证项；明确理解通过不等于代码正确或可发布。
- **下一步**：一项具体且可在 2 分钟内开始的行动；仅在用户设置了合并条件时报告该条件是否满足。

不要在结束后擅自写入仓库规则、测验记录或长期记忆。只有用户明确要求以后每次交付都进行答辩时，才按其指定范围配置持久触发规则；技能自身不会自动为所有项目建立这一规则。
