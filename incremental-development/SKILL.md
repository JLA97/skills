# 复杂改动的增量开发

目标：每次交付一组能够解释、验证和继续维护的行为变化。先消除不必要的复杂度，再管理剩余复杂度；不要把过度设计拆成更多步骤后照样实施。

## 1. 判断与简化

- 读取相关代码、项目约定和已有任务记录，以当前需求及实际实现为依据；未知信息明确标为假设，仅询问影响方案的缺口。
- 简短说明复杂点以及是否需要分步推进。不要为判断复杂度先生成完整规划。
- 优先复用现有模式和设施。对重要的新增依赖、服务、后台任务、持久状态或通用抽象，回答：
  1. 不引入它，哪个当前要求无法满足？
  2. 更简单的办法为什么不足？
  3. 增加了哪些理解、部署、配置、监控、排错或恢复负担？
- “未来可能扩展”不能单独证明必要性。暂不引入的机制，必要时记录可观察的重新评估条件；性能问题未经测量时标为假设。
- 不通过省略当前要求所需的正确性、安全性和失败恢复机制来简化设计。
- 简化后若已成为普通局部改动，说明结论并按正常开发完成，退出完整切片流程，不额外创建计划和进度文件。显式调用本 skill 也不意味着必须拆分。

## 2. 定义最小方案与切片

保留一份简短方案：目标、非目标、最小实现方式、必要的新机制及其代价。不强行提供多个方案；有实际取舍时再比较。

- 按可观察行为切分，尽量贯通输入、核心逻辑和结果。每个切片写清预期行为、边界、验收方式与前置依赖。
- 同时只推进一个切片。按依赖排序，优先验证最不确定且会影响整体方案的部分。
- 避免按 Controller、Service、Repository 等技术层先铺大量不可用骨架。纯内部改动可用明确的接口契约或可观察性质验收。
- 保持一个行为必需的不变量完整。例如要求整批原子写入时，事务与失败验证属于写入切片，不能推迟到后续补齐。
- 切片过大时缩小业务范围，不用固定文件数或代码行数限额替代判断。
- 必须先探索时，使用有明确问题、验证方式和退出条件的小实验；实验成功不等于生产功能完成，不把临时代码自动纳入交付。

## 3. 实现与实际验证

- 开始实现前确定验收行为，避免用当前实现反向定义“正确”。不夹带无关重构或未来功能。
- 在授权范围内完成当前切片，运行与风险相称的检查。优先复用有效测试；新增测试应能发现真实行为错误，不只复述实现。
- 对状态、并发、重试或持久化变化，验证对应的关键失败路径与不变量；构建成功不能代替行为验收。
- 用具体输入简述实际调用路径与结果，关联关键文件、函数或测试，避免只提供抽象架构描述。
- 分开记录实现状态和验证状态。未执行、未通过与已通过不可混用；说明验证覆盖范围，不能由局部检查推断整个系统正常。
- 关键验收失败时先修复当前切片，不用继续堆功能掩盖问题。环境受阻时保留未验证状态，说明阻塞条件；不将依赖此结果的后续切片视为可交付。
- 当前切片通过后，继续既定授权范围内的下一片，不逐片请求确认。新增重大机制或改变关键语义时先更新方案、解释偏离；已有授权不足才询问用户。

## 4. 保存与恢复

确实需要多个切片、预计跨会话，或中断后难以恢复时，维护一份任务记录。优先复用现有 Issue、PR 或本地任务文件；没有适合载体时，在项目允许的位置创建一份 Markdown 文件。不要为简单任务建账本，也不要把临时进度写入 AGENTS.md。

记录保持精简，以当前事实为主，不复制聊天历史：

```text
目标与非目标：
最小方案与关键取舍：新增机制、必要性、维护代价
切片列表：预期行为、验收方式、依赖、实现状态、验证状态
当前代码状态：已有提交号，或未提交的相关文件与差异范围
最近验证：命令/操作、实际结果、对应代码状态、未覆盖范围
恢复入口：关键文件/函数、未完成项、阻塞条件、下一步具体动作
```

- 每个切片结束、方案发生实质变化或可预见的中断前更新记录。依赖平台工具保留的日志时，保证恢复记录能定位证据；不要记录密钥或敏感原始数据。
- 代码在验证后发生相关修改时，旧结果不能作为新版本的通过证据。记录尚未重新验证的范围。
- 复用已有 Git 历史，按项目约定和用户授权创建提交；不为打检查点而自动提交用户的其他改动。
- 恢复时先读记录，再核对工作区差异及相关代码，必要时执行最小基线检查。记录与代码冲突时先查明差异，不能盲信“已完成”。
- 保留用户已有改动；不要通过重置、覆盖或清理工作区来伪造干净的恢复状态。

## 5. 交付

简洁报告已完成的行为、关键复杂度取舍、实际验证、剩余限制和恢复记录位置（如有）。流程执行完毕不能替代功能完成；不得声称用户已经理解或掌握代码。

## 判断示例

- 按现有模式增加一个普通 CRUD 字段：通常直接完成，无需完整流程。
- 机械替换几十个文件中的名称：文件多不代表需要功能切片。
- 少量代码改变任务状态一致性或重试语义：需要检查复杂度、保持不变量并验证失败路径；不强行为一个不可分割的修复造出多个切片。
- 给单一导入场景提出插件框架与消息队列：先检查当前要求是否需要这些机制；删减后若变简单，退出完整流程。
- 增加任务创建、执行、取消和重启恢复：先明确状态与依赖，再分片实现，保留每片验证证据和恢复入口。
